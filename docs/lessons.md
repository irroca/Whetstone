## 1. 研究层面：值得讲的发现

按「如果只能讲五件事」的顺序。

### 1.1 RL 推高的是准确率本身，不只是格式

- 29M 的玩具模型上，GRPO 的 accuracy 在 150 步里**始终是 0.000**，`hack_rate` 与 `format_rate` 逐点相等：
  每一条格式正确的回答答案都是错的。策略只优化了它够得着的奖励分量（experiments「What both runs actually learned」）。
- 100M 模型 + SFT 冷启动后，12 个跑次的 test 准确率从 SFT 的 0.628 升到 0.938–0.962，格式从头到尾是 1.000，
  平均回答长度几乎不变（36 个 token）。两位数题基本做对（加法 0.986、减法 0.976）。
- **为什么环境要把 `accuracy` 和 `format` 分开记、并单独算 `hacked_format`**：一条标量奖励曲线在 29M 那批跑里
  会看起来像稳步进展。这是整个项目里最值得写的「评估设计」小节。

### 1.2 零奖励是 GRPO 的吸收态

- 29M 的两个对照跑：不加 KL 的那个在第 50 步前后崩溃，之后奖励处处为 0 → 每组方差为 0 → 优势为 0 →
  `grad_norm` 恰好为 0，持续 100 步；熵从 3.75 掉到约 1.3，策略退化成重复一个 token。同样的学习率和种子，
  只加 `--kl_coeff 0.02` 的那个熵稳在 2.0 左右，格式率单调升到 0.915（experiments「Runs B vs C」）。
- 结论的措辞：KL 项在这里的作用不是温和的正则，而是**不让这次训练死掉**。
- 反面：100M + 63% 的 SFT 起点上，同样不加 KL 熵也从 0.028 降到 0.003–0.004，但准确率一路在涨、没有退化——
  因为这个起点有混合组，没有崩溃可防。「KL 要不要」取决于起点有没有奖励方差。

### 1.3 冷启动：不够会全 0，太足也会全 0

- 策略不会输出环境格式 → 全组零奖励 → 梯度恒为 0（算术环境，29M）。
- 反过来 SFT 训到完全饱和也会让采样没有方差。代码环境里量到的版本更极端：
  - 在 22 个模板族上 SFT（loss 0.0000）：见过的族 1.000，没见过的 0.000，RL 没有可改善的地方；
  - 只在 12 个族上 SFT，另外 10 个族 0%，GRPO 探针里 `acc` 0.00、`silent_group_frac` 1.00、`grad_norm` 恰好 0；
  - 每个其余族给 3 条示例，才有信号：采样准确率约 0.3，静默组 0.53–0.75。
  - 每族 3 条示例的结果是「整族对或整族错」（4 个族 1.00，6 个族 0.00）：模型把每个族背成一个模板。
- 博客角度：**冷启动不是「做了 SFT 就行」，而是要让 SFT 后的策略恰好落在「有的会、有的不会」的区间**。

### 1.4 `--ppo_epochs 1` 时截断从不触发（DAPO 的 clip-higher 因此是空操作）

- 每批 rollout 只更新一次，旧 log-prob 又是在更新前用同一份权重重算的，重要性比恒为 1，12 个跑次的 `clip_frac`
  每一步都是 0。
- 数字没出来之前，容易把 DAPO-lite 与别的变体的差别归因给 clip-higher；这在 `--ppo_epochs 1` 下不成立，所以不能这么写。
- 三位数的跑次里 `--ppo_epochs 2` 让截断第一次触发（`clip_frac` GRPO 0.1–0.2%，DAPO-lite 0.3–1.0%），
  但准确率上没有可见收益。
- 同一轮里还量到：Dr. GRPO 的梯度范数约小 7 倍，DAPO-lite 约大 12 倍，而 AdamW 除以梯度的滚动均方根，
  常数缩放几乎不改变更新，所以四条 dev 曲线重合。**「变体之间没差别」背后有三个可以点名的机制**
  （截断不触发、长度几乎不变、梯度尺度被 Adam 吸收），不是「算法没用」。

### 1.5 四个 GRPO 变体分不出高低；更难的题上也只是「一致但不能下结论」

- 一两位数：test 平均 0.942–0.955，种子标准差 0.4–0.7 个点，单个 500 题分数在 0.95 附近的二项标准误约 1 个点；
  dev 和 test 给出的排序不同（Welch t ≈ 2.7、约 3 个自由度，p ≈ 0.07，还没做多重比较校正）。
- 三位数：SFT 起点 test 0.290（三位数 0.038），GRPO 300 步到 0.54–0.59；Dr. GRPO 和 DAPO-lite 比 GRPO 高约 4 点，
  配对 McNemar p ≈ 0.01。**但同一个 GRPO 的两个种子是 0.544 和 0.512**，种子间差 3.2 点，与变体间的差距同量级。
  McNemar 的 p 只数题目、不含种子间的波动。
- 值得写成一节的方法论：**一个跑次内的配对检验回答的是「这 500 道题上谁更好」，不是「这个变体更好」**。

### 1.5b 种子网格：变体之间的差距小于种子之间，而且有四个跑次不再停止

- 三位数加减法，3 变体 × 3 种子 × 600 步（4090，6.6 小时）：test 均值 0.686 / 0.699 / 0.724，同一变体的种子标准差 4–7 点；
  同一对变体在三个种子上的配对检验结论互相矛盾（p 从 0.07 到 3e-12，方向还翻转）。Mac 上 300 步一个种子看到的「4 点领先」没有复现。
- **回答长度失控**：9 个跑次里有 4 个在中途突然不再输出 EOS，回答写到 token 上限（`</answer>6</answer>6…`）；三个变体都出现过，
  起点从第 55 步到第 226 步，是几步之内的突变；这些策略在 `</answer>` 之后的 EOS 概率从 1.0 掉到约 0。奖励只看第一个答案，
  没有东西把它拉回来。每步变慢约 2 倍，长度统计也失效。**原因没有验证**。把「没有 EOS 的采样按错处理」(`--truncated_reward 0`)
  加上后重跑这 4 个格子，全部不再失控，准确率 3 升 1 平，种子标准差从 4–7 点降到 2–4 点，变体的排序又回到 Dr. GRPO / DAPO-lite
  比 GRPO 高约 4 点（约 1.5 个标准误，仍不能下结论）。**失败模式的噪声可以淹掉变体之间的差别**：先修失控再比变体。
  另外：没有任何奖励改变时 CUDA 上的 GRPO 跑次逐题复现（`grpo_s1` +0 −0）。
- 博客角度：「一个跑次里的显著」和「一个变体的显著」是两件事；以及**监控平均长度和截断率**，准确率曲线对这件事是瞎的。

### 1.6 DPO 单独用学不到东西，原因可以量出来

- 手工损坏的偏好对对 SFT 策略太容易：它已经把留出的对 **100%** 排对，对数概率差 51 nats。lr 1e-5 跑满 1 个 epoch 把格式打坏（dev 0.000）；
  lr 1e-6 与 SFT 没有差别（test 0.626 对 0.628）。中间的 20 / 40 步停止是 dev 0.610 / 0.518。
- 换成 `mine_pairs.py` 从策略自己的采样里挖的 2022 对：排序准确率 0.821 → 0.849，但贪心准确率没有跟着动
  （dev 0.648、test 0.576）。
- 这是一个「loss 在降、准确率不动」的好例子：DPO 的 loss 即使在降，也可能只是把一个已经成立的排序拉得更开。
  看 `accuracy`（隐式奖励差 > 0 的比例），别看 loss。
- 局限：每个设置一个种子，dev 和 test 的方向相反（+1.2 与 −5.2），这个差距有多少是噪声，一个种子说不清。

### 1.7 预训练本身的数字

- 99.5M 参数，9.914B token 一个 epoch，18,919 次更新，H800 PCIe 上 8.29 小时、一次跑完（没有崩溃、没有续训）；
  最终验证 loss 2.5539（ppl 12.86）；没有 loss 尖峰，预热后梯度范数中位数 0.276、最大 0.568，没有一次更新被裁剪。
- 每个来源的 bits per byte：zh 1.297、en 1.006、code 0.593、math 0.881；比数据消融的 25.7M 代理模型分别好
  21% / 20% / 33% / 26%（计算量比约 100 倍，只作粗略参照）。
- 基座的算术：4-shot 一位数加法 22%、两位数 2%。样本里看得到「抄上面例子的答案而不是做加法」。
- 数据消融：中文 15% 之前就拿到了九成收益（0→15% 中文 bpb 降 1.249，15→45% 只再降 0.131），中文 0% 的组 39% 的
  中文提示续写成英文；最终定 20%；词表 16k→32k 加权平均降 1.9%，32k→48k 只再降 0.8%，所以定 32k。

## 2. 数据管线的坑（数据比模型更容易出错）

出处：status §4 步骤 3「跑出来并已修掉的十一个问题」、步骤 5、AGENTS.md 的数据管线条目。

| 现象 | 原因 | 修法 / 教训 |
|---|---|---|
| JSONL 读取器「一直在丢数据」 | 每篇只取前 `max_seq_len` 个 token：冒烟语料上只用到 28% 的 token，书籍 1%，配比里书籍从 6.4% 变成 0.2%；loss 照常下降，不报错 | 预训练改读 `tokenize_corpus` 产出的 `.bin`；**配比消融只在 `.bin` 上有意义**。这是换 memmap 最重要的理由，比内存和速度都重要 |
| FineWeb2-HQ 中文那份比正文大 9.3 倍 | 每行带 768 维 embedding，上游列被原样写出；下载时 fsspec 又预读 5MiB 读进 embedding 列 | `to_record` 只投影 schema 字段；parquet 源用 `hf.columns` 裁列并把预读调成 64KB（1000 行：25.6MB → 3.8MB）|
| 书籍的保留率报告失真（报 18%、实际约 89%） | 按 256 条一批 tokenize，预算在批中间填满后，剩下的记录全被计入「读取」 | 每条记录带计数快照，填满时回退 |
| 去污染误杀 3.9% 的文档，几乎全是假阳性 | 标点算作 n-gram 单元（一串 `-` 命中所有 markdown 表格）；短答案按 n-gram 索引（MMLU 的 `1,2,3` 一项命中 76 篇） | 标点不算单元、短答案只精确匹配、题干至少 8 个单元；选择题把选项拼进 `question`；消融池上 252 → 57 篇 |
| 去污染的 LCS 复核让短题「碰巧」凑够分，又看不到长文档深处的真泄漏 | 原先对整页算 LCS，且只截前 2000 个单元 | 改为在共享 n-gram 处对齐（±上下文）再算 LCS；剩下的两处 13-gram 命中（一张公式表与 MATH-500 一题共享行列式；MMLU 一题引用的《独立宣言》）得分 0.51 / 0.59，保留。**每次「发现泄漏」都要看原文** |
| 去污染要覆盖代码 | 代码评测集（HumanEval、MBPP）要带测试拉进来 | 参考实现放 `answer`（短答案只精确匹配）；放 `solution` 会按自身长度索引，一句 10 个单元的惯用写法就会误杀所有用到它的文件 |
| 49% 的 starcoderdata 文件第一行是 `<reponame>…<filename>…<gh_stars>…` | 数据集自带的元数据 | 加 `cleaners`，只删整行都是元数据的行，代码里的 `'-f <filename>'` 不动 |
| 重复度规则系统性地删长代码文件 | 字符 10-gram 重复度随文件长度增长（缩进、样板），2k 字符内拒 2%、2 万字符以上拒 57%，几乎全是正常源码（232 篇里只有 10 篇是生成代码） | 代码源关掉这条规则，保留率 80% → 94% |
| 重复行比例把单独一行的 `"""`、`)`、`},` 也算进去 | docstring 多的文件显得一半是重复行 | 只统计含字母或数字的行 |
| `prepare --probe` 打印完结果后卡死不退出 | pyarrow 25 在还有 parquet 读请求没完成时退出，会死锁在线程池的析构里；`del`+`gc.collect()`、关 `pre_buffer` 都不管用 | 入口跑完 atexit 后直接 `os._exit`；**别改回普通的 `main()` 调用** |
| 第一次正式构建丢了 3.6 小时 | 断网 13 分钟，HF 客户端自己在重试，但这期间又手动起了两份 `run.sh`，它们以 `"w"` 重开输出文件，把 7.9GB 的文件截成实际只有 339MB 的稀疏文件 | 两层锁（`run.sh` 加锁、`prepare` 锁 `--out_dir`）；按源续跑；**日志里刷 `Retrying` 时不要手动重启** |
| `import datasets` 报 `cannot import name 'load_dataset'` | 没装 HF `datasets` 时，本地的 `datasets/` 数据目录被当成同名的命名空间包 | 把 `datasets` 写进 `requirements.txt`；报错信息本身极具误导性 |
| 消融的验证 loss 只测了中文 | `build_val_loader` 按文件顺序读，`prepare` 写出的划分按源分组，`--val_batches` 只评估前几个 batch，就是 zh_web | 验证集按一个固定的排列读，每次评估还是同一批样本，但取自整个划分 |
| 数据池比 train 划分大 | 数据池按全部文档定量，但组和分词器样本只读 train 划分 | 目标除以 train 的占比 |

通用教训：**「静默」的失败比报错的失败贵得多**——丢数据、误杀、截断成稀疏文件，没有一个会报错，
都是靠核对计数、抽查原文、对账配比才发现的。管线里的每一步都应该输出一份「我删了什么、为什么」的报告，
并且这份报告本身要可信（`fill < 100%` 要报警、`kept%` 不能含未发出的记录）。

## 3. 训练工程的坑

### 3.1 注意力：SDPA、`is_causal`、`torch.compile`、cuDNN

- **续写不能用 `is_causal=True`**：SDPA 的因果 mask 左上角对齐，`q_len < kv_len` 时新 token 看不到自己前面的缓存。
  单测故意把条件改坏过，续写的两个用例会失败。
- **MPS 上 SDPA 反而更慢**：训练时仍然物化 score 矩阵，seq 2048 只省 15% 显存，还慢 7–8%；所以 MPS 一律走显式路径。
- **cuDNN 注意力要在被编译函数「里面」选**：PyTorch 自己的顺序把 cuDNN 排在 math 之后，不会自己选；
  `torch.compile` 不理会函数外面的 `sdpa_kernel(...)`，也不理会 `enable_flash_sdp(False)` 这类全局开关，
  编译出来照样是 flash；eager 下两种写法都生效，所以很容易以为已经换了后端。只有在被编译的函数内部进入
  `sdpa_kernel(order, set_priority=True)` 才生效。用 `torch._dynamo.explain` 确认这样仍是一张图、零 graph break。
- **逐个改、逐个量**（H800 PCIe，batch 32，编译）：起点 270,547 token/s → 损失一起编译 +9.9% → 实数 RoPE +5.0% →
  原生 GQA +0.2%（显存 −1.7GB）→ cuDNN +9.4%，合计 +26.5%。每个改动一个提交、一份 bench 记录。
  只编译模型留下的 eager 交叉熵会把整个 logits 转成 fp32 再反传一份同样大的 fp32 梯度，占一步的 14%。
  Inductor 不给复数算子生成 kernel，复数 RoPE 退成一串 eager kernel（5% 的一步）。
- **试了没用的**：加大 batch（cuDNN 下 batch 16 / 32 / 64 是 33.4 / 34.2 / 34.5 万 token/s，显存多用 3.6 倍只快 3%）、
  `coordinate_descent_tuning`（+0.75%，与同配置两次 bench 的差距约 0.5% 同量级）。**做了对照：优化前后同种子同数据的试跑，
  到第 200 步 val 只差 0.001**，是换 kernel 和归约顺序后的正常抖动——优化没改数值。
- **`nvidia-smi` 的 100% 利用率和 45GB 显存说明不了什么**：利用率是「至少有一个 kernel 在跑」的时间占比，
  显存是缓存分配器的保留量（其中约 16–20GB 是验证留下的）。看 MFU：33.78 万 token/s × 0.710 GFLOP/token = 240 TFLOPS，
  标称峰值 756 的 31.7%；但这张 PCIe 卡一直顶着 350W 功耗墙，按实际频率算可达峰值只有 525–616 TFLOPS，MFU 合 39–46%。
  Llama 3 405B 在 H100 上是 38–43%，这个规模的小模型逐元素开销占比大，MFU 结构上就高不了多少。

### 3.2 训练循环

四份几乎相同的 `train_epoch`，问题也是四份，合成一个 `trainer.train` 时一次修掉：

- 验证和存档在每个 micro-batch 上判断：累积 16 步时，`global_step` 停在 1000 的那 16 个 micro-batch 每个都触发一次。
  改成只在优化器更新之后判断，`--log_step` 等都按更新计数。
- **续训不保证数据相同**：`shuffle=True` 每次重新打乱，RNG 状态不进 checkpoint，dropout 的随机数也接不上。
  改成每个 epoch 的顺序由 `seed + epoch` 决定的排列，checkpoint 里存「本 epoch 已消耗的 batch 数」和 RNG 状态；
  DataLoader 的 generator 也要固定，否则它每创建一次迭代器就从全局 RNG 取一个种子，把续训的 dropout 错开一位。
  单测断言续训后**每个参数逐位相等**，且故意去掉三处中的任何一处都会失败。
- checkpoint 原地写：租的卡会被回收，写到一半新旧两份一起坏 → `atomic_torch_save`（临时文件、`fsync`、`os.replace`）。
- 每个 micro-batch 都 `loss.item()`：强制 GPU 同步，白白损失吞吐 → 指标在设备上累加，记日志时才读。
- 优化器是 `AdamW` 默认值：对 RMSNorm 的增益也做 weight decay → 只对二维以上的权重 decay，β₂ 0.95。

### 3.3 GRPO / rollout

- **只有等长的 prompt 能同批 `generate`**：模型没有 left-padding 的 RoPE 偏移，所以 `run_rollouts` 按长度分桶。
  100M 模型逐 token 解码受调度开销限制（MPS 上 1 行 11ms、32 行 18ms、128 行 47ms），分桶后 500 题贪心评测快约 20 倍。
- **`generate` 产出的 token id 必须 `clone()`**：inference_mode 张量参与需要 backward 的前向会报错。
- **旧/参考 log-prob 要重算**：温度和 top-p 改变采样分布，重要性比需要策略自己的分布。
- **微批必须共用整批的分母**（`normalizer`），有单测断言「分块损失之和 == 全批损失」。
- **`loss` 恒为 0 是数学必然**（on-policy + `seq_mean` 时 ratio ≡ 1 且组内优势和为 0），看 `grad_norm`。
- **大 batch 配 `--micro_batch_size`**：32 题 × 8 条在 48GB 的 Mac 上不分块把内存换页换满，每步 22–153 秒，分块后约 9 秒。
- **SFT 样本要带环境的 system prompt**：没有的话 chat template 会补上默认的 system prompt，而 GRPO rollout 用环境自己的——
  冷启动训的 prompt 和 RL 看到的不是同一个。现在 SFT 和 DPO 的样本编码后与 `rollout.build_prompt_ids` 逐 token 相同，
  有单测断言；`SFTDataset` 也按每轮的 `role` 编码（只有缺 `role` 时才按奇偶）。
- **repetition penalty 的符号**：以前不分 logit 正负一律除，负 logit 的 token 反而被抬高；现在与 HF 一致（正除负乘）。
- **评测题要显式排除**：一两位数加减法只有约 1.5 万道题且一半至少有个一位数，独立抽样时 4000 条 SFT 集含评测集 55% 的题，
  评测集自身也只有 432 道不同的题。`--exclude` / `--distinct`；一位数的题只有 155 道，dev/test 拿走 134 道，
  所以一位数组的分数量的是泛化而不是「简单题」。
- **过早停止 / 调度**：20 步的试跑里 10% 的预热只有 2 步，第 2 步就到了满学习率，dev 反而从 0.636 掉到 0.588；
  换成与正式相同的 100 步设置诊断，涨到 0.764。**小规模试跑的调度要按总步数缩放**。

### 3.4 代码环境（沙箱 + 模板族）

- **沙箱不是安全边界**：子进程 + 独立 session + 墙钟超时 + 每用例 alarm + `RLIMIT_CPU`/`RLIMIT_FSIZE` + 禁用进程/网络模块
  + 空环境。对 100M 策略的 bug 够用，对有意越狱不够；代码和文档里都明说，真要用不可信来源就上一次性容器。
- 部分得分（`partial_weight`）默认关：6 个用例下，永远返回最常见输出的函数就能拿到约 0.3 的通过比例，策略会先找到它、再找算法。
- 打分并发：一个沙箱进程约 5–25ms，`score_many` 用线程池；曾怀疑 `fork` 一个装着 torch 的大进程会很慢，
  实测每次约 5ms，不是瓶颈。真正慢的是模型侧（长序列加换页），每步约 30 秒是算力受限。
- **模板化环境的局限**：26 个族的题是模板，SFT 把每个族背成一个模板；这衡量的是「RL 能不能把会写的变成稳定写对」
  以及对没见过的族的迁移，不是通用编程能力。HumanEval / MBPP 仍只做去污染。

## 4. 基础设施与运维的坑

### 4.1 AutoDL

- 无卡模式（0.5 核、2GB 内存）能做的事要在开卡前做完：上传、校验、CPU 预检；做不了 CUDA 相关的，也别在上面
  跑 `prepare` 或 `tokenize_corpus`。2GB 内存下 python 到 1.5GB 上下就被 SIGKILL（退出码 137，cgroup 的 `oom_kill` 计数却是 0）。
- **`nproc` 报的是宿主机 176 核**，torch 照它开线程池：0.5 核时一次更新要 188 秒，`OMP_NUM_THREADS=1` 后 1.4 秒。
  `env.sh` 按 `/sys/fs/cgroup/cpu.max` 设线程数，同时设 `PYTHONUNBUFFERED=1`（输出重定向到文件时 Python 按块缓冲，
  `train.log` 里一行进度都看不到）。
- 数据和 checkpoint 都别放系统盘（30GB）；`/root/autodl-tmp` 实例释放就没了。
- 网关会一次断开所有连接；`xargs` 碰到退出码 255 会放弃剩下的全部输入，所以上传脚本失败一律返回 1，由下一轮补传。
- 从 GitHub Release 下载只有 70–150 KB/s；`gh release download` 在 398MB 的权重上 45 分钟读超时，留下半个文件，
  `--skip-existing` 重跑时还会把它当成已下完 → 改用 `curl -C -`；`gh api` 会把错误响应追加进半个文件。
  GitHub 上传反复 408；魔搭上传 1GB 以上常写超时；**从无卡实例直接传魔搭很快（398MB × 13 份 6 分钟）**。
- AutoDL 默认的阿里云 pip 镜像在 4090 实例上返回 403，清华源和腾讯源正常。
- 本机新版 OpenSSH 的 `scp` 走 SFTP，远端路径里的 `{a,b}` 不会展开。
- `nvidia-smi` 在无卡模式下报权限错误是正常现象。

### 4.2 Mac（MPS）

- **bf16 而不是 fp16**：fp16 autocast 把 100M 模型的 loss 从 −0.3278 推到 +0.0018，bf16 保持 −0.3276。
- **`--device` 默认要选 mps**：裸的 `"cuda" if available else "cpu"` 在 Apple Silicon 上悄悄慢约 6 倍（1.4k vs 9.1k token/s）。
- **训练不逐位可复现**：同配置同种子的两次 SFT，dev 准确率 0.618 与 0.650。CUDA 上 SFT 是逐位可复现的。
- **内存换页**：连续跑几个长任务后，swap 用到 25 GB / 26.6 GB，一步从 10 秒变成几分钟，进程长时间处于 `U` 状态。
  已经停掉了两次跑次。经验：一次排两三个跑次、中间留空；别在训练同时跑别的重活。
- **后台任务的存活**：用 `nohup … &` 在工具调用里启动的进程会随这次调用结束而被杀；要用工具自带的后台 shell。
  更早的消融是在 `screen` 里跑的，因为挂在 agent 的 shell 下，退出 Cursor 会连带杀掉训练。
- macOS 自带 bash 3.2：`set -u` 下空数组会报错，要写 `${flags[@]+"${flags[@]}"}`。
- 管道里 `| head -1` 提前关管道，下游 Python 在后面的 `print` 里 `BrokenPipeError`，**如果结果文件在打印之后才写，就丢了**
  （这次真的丢了）。结果文件要先写再打印。
- 环境：Python 3.12 + venv（macOS 自带 3.9 跑不了 `transformers` 5.x）；`HF_HUB_OFFLINE=1`（不设的话测试 47 秒，设了 16 秒）。

### 4.3 Git / PR

- **stacked PR + squash 合并出过两次事故**：#5 的 base 是 #4 的分支，#4 squash 合入 `main` 之后 21 秒 #5 才合进 #4 的分支，
  结果 `main` 拿到的是 #5 之前的树，#5 显示「已合并」但工作全留在 #4 的分支上。教训：stacked PR 要么严格自下而上合，
  要么合之前把上层 PR 的 base 改成 `main`。
- **往已有 PR 推提交之前先 `gh pr view <n> --json state`**：#10 合并之后又往它的分支推了 5 个提交，GitHub 照样显示「已合并」，
  但那 5 个提交不在 `main` 上。补救是 `git rebase --onto origin/main <原末端>`，squash 提交与原末端 tree 相同时不改任何 tree。
- 这一轮的做法：每个 PR 都直接基于 `main`，彼此不依赖；有依赖时在 PR 描述里写明；`status.md` 这种大家都要改的文件
  等前面的合并后再单独一个 PR。
- 并行的 `Write` 和后面依赖它的 `Shell` 会赛跑（文件还没写完就被读）——有依赖的调用要等前一个返回。

### 4.4 公开仓库与不便公开的机器

- 仓库是公开的。在一台不便公开的电脑上产生的记录要先**脱敏**（主机名换成 `redacted`、绝对路径改成相对）再提交：
  `scripts/redact_records.py` 做这件事，并且在发现还有漏网的标识符时退出码为 1；`tests/test_redact_records.py` 测它。
- Git 身份只设在仓库本地，不碰全局配置。
- 令牌的规矩：不读、不回显、不放进 argv；GitHub 令牌只经 stdin（`curl -K -`）传；HF 主令牌**绝不**发给镜像，
  公开 gated 数据集走镜像时用专门建的、只读公开仓库的细粒度令牌，用完删除。
- 权重和语料在两个私有仓库（魔搭、GitHub）各存一份，`docs/artifacts.md` 列每个文件是什么、谁读它；
  一个没有标签的 `.pth` 就是把跑次弄混的开始，所以新产物一律是 `<stage>-v<N>` 组，带自己的 README 和 SHA256SUMS。

## 5. 方法与评估上的教训

1. **先量再说**：这个项目里被「实测」推翻的判断有一长串——「SDPA 在 MPS 上会更快」（慢 7–8%）、「clip-higher 解释 DAPO-lite
   的差别」（截断根本不触发）、「DAPO-lite 熵更高因为探索更多」（过滤只留下了不确定的题）、「GPU 利用率 100% 说明算力用满」
   （MFU 31.6%）、「消融的验证 loss 反映混合配比」（它只测了第一个源）。**把推翻过程写出来比只写结论更有说服力**。
2. **跨词表别比 loss**：词表大的每个 token 要预测的信息更多；消融用每个来源的 bits per byte。
3. **`single_char_frac` 只能在同一书写系统内比较**：中文单字本来就是有意义的单位，63% 是正常的。
4. **p 值要说清数的是什么**：McNemar 数题目、Welch t 数种子；两者回答的问题不同，一个种子的变体对比两者都不够。
5. **held-out 要显式排除、要报分层**：见 3.3 的评测题污染与一位数组。
6. **每个跑次都记录一切**：`runlog` 的 `meta.json` 记 git 提交、脏标记、输入文件指纹；`metrics.jsonl` 逐行 flush，
   被杀的跑次也留得住点；训练和评测记成分开的行，否则 reward/kl/entropy 会被归到验证集下。
7. **尽量让数字能从仓库重算**：`records/posttrain_v1/summarize.py`、`records/posttrain_v3/summarize.py` 重算文档里的每个数字。
8. **诚实地写没做完的**：代码环境的 GRPO 第一次因内存换页停掉、DAPO-lite 的第二个种子停在第 60 步，文档里都写明了，
   后来重跑完成时再把结果补上，而不是换个说法带过。
9. **别让「静默成功」蒙混**：`fill < 100%` 要报警、`ran out of data` 要显眼；去污染的 `top_matches` 中删得最多的一项就是
   通用短语的签名，先看它再决定放宽哪条规则。

## 7. 诚实的局限（写博客时别回避）

- **种子**：三位数网格有 3 个种子，但每个种子一个 SFT 起点、一个学习率；种子间标准差 4–7 点，比变体间的差距大。其余实验多数只有一个种子。
- 算术任务是 1–3 位加减法，模板化、答案唯一，是验证 RL 流程的试验台，不是推理能力的证明。
- 100M 模型离 HumanEval 很远；代码环境是 26 个模板族，这是受控实验，不是编程能力。
- 代码环境的 RL 每个变体一个种子、200 步：整族提升、不迁移、GRPO 忘掉了一部分只在 SFT 里见过的族，原因没有验证。
- DPO 的对比一个种子，dev 和 test 的方向相反。
- 蒸馏：金标准数据上的 logit KD 没有超过 SFT（学生 test 0.475 对 0.384–0.451，三个种子），机制只是假设；学生上的 GRPO 一个种子。
- 变体对比的结论强度：一两位数上分不出高低（有三个可点名的机制），三位数上「一致但种子数不够」。
- 沙箱不是安全边界。
- 数据消融用的是 25.7M 的代理模型、3 亿 token，与正式的 100M / 100 亿 token 的比较只是粗略参照。
